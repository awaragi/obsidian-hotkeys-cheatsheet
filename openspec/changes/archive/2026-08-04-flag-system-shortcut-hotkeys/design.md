## Context

"By Most-Used Shortcut" sort mode (`sortByMostUsedShortcut` in `sortHotkeys.ts`) includes orphaned signatures — captured keypresses with no currently-bound Obsidian command — as pseudo-entries labeled "No command" (`grid.ts` `renderFlatList`, `en.json` `modal.no_command`). Some orphans, like `Cmd+V`/`Ctrl+V` (paste), are OS/Electron-level shortcuts intercepted before Obsidian's command system ever sees them; they can never be bound to a command. Today they render identically to genuinely free combinations a user might plausibly bind, which is misleading.

Investigation of the existing signature format (`buildSignature`/`dedupeModAlias` in `usageTracker.ts`) found that `Mod` already abstracts `Cmd` (macOS) and `Ctrl` (Windows/Linux) into one canonical token — the same physical "paste" keypress produces the signature `Mod+V` on every platform. This means detecting these system shortcuts does not require any OS-specific branching or `Platform` lookups: a fixed, platform-agnostic signature set is sufficient.

## Goals / Non-Goals

**Goals:**
- Flag orphaned signatures that match a known OS/Electron-reserved shortcut, or a default Obsidian editor command binding likely to explain an otherwise-unbound signature: clipboard/selection, undo/redo, line/document navigation + delete, selection-extension, and word-wise navigation.
- Give each flagged signature its own descriptive label (e.g. "Copy", "Paste", "Move to Line Start") instead of one shared generic label — and, where the signature's real-world meaning differs by platform, a label specific to macOS vs. Windows/Linux.
- Distinguish flagged rows from generic "No command" orphans via a leading lock icon + tooltip, while keeping the same muted text color as other orphan rows (not a separate accent color).
- Keep the detection lookup (is this signature flagged at all) pure and platform-agnostic; keep the label lookup pure but platform-*parameterized*, taking `isMac` as an explicit argument rather than importing `obsidian` itself.

**Non-Goals:**
- Exhaustively cataloguing every OS/Electron-reserved shortcut across all three platforms (e.g. window management, app-level shortcuts like quit/minimize). Set is scoped per user request; easy to extend later.
- Verifying Windows/Linux behavior on real hardware — the user does not have a Windows/Linux machine to test on. Labels for those platforms are best-effort, based on well-documented OS text-editing conventions, with the lowest-confidence entries (`Alt+Left/Right` → back/forward navigation) called out explicitly in code comments.
- Hiding or filtering these orphans out of the list — they remain visible, just visually distinguished.
- Changing behavior of any other sort mode; orphans already only surface in "By Most-Used Shortcut" (unchanged requirement).

## Decisions

**Fixed `Mod`-normalized signature set for the platform-invariant entries; no per-platform detection needed for those.** For clipboard/selection, undo/redo, and the `Mod+Arrow`/`Mod+Backspace`/`Mod+Shift+Arrow` families, the canonical signature already normalizes `Cmd`/`Ctrl` via `Mod`, and all of them are consistently OS/Electron-intercepted on every platform even though their exact native behavior (e.g. line-wise vs. word-wise navigation) isn't identical — that's the only thing detection needs to know, so no platform branching is needed for these.

**Detection *is* platform-parameterized for the `Alt`-based entries, revising the original "fully platform-agnostic" decision.** The user confirmed that `Ctrl+Arrow`, not `Alt+Arrow`, is the real word-jump shortcut on Windows/Linux, and asked to drop the `Alt+Arrow` → "Navigate Back/Forward" guess for that platform entirely rather than keep an unverified label. Since `Alt+ArrowLeft/Right` and `Shift+Alt+ArrowLeft/Right` (word jump / word selection via Option) have no confirmed Windows/Linux meaning, `isSuspectedSystemShortcut` now also takes `isMac` and simply delegates to `systemShortcutLabelKey(signature, isMac) !== undefined` — a signature with no label on a given platform is, by construction, not flagged there either. This keeps the two functions from ever disagreeing (single source of truth: the label tables) at the cost of `isSuspectedSystemShortcut` no longer being platform-agnostic as originally designed.

**New module `src/ts/usage/systemShortcuts.ts`, now a signature → label-key map rather than a plain set.** Originally a `Set<string>` behind `isSuspectedSystemShortcut`. Revised to a `Record<string, TranslationKey>` (`SYSTEM_SHORTCUT_LABEL_KEYS`) so each signature carries its own specific i18n key, exposed via two functions: `isSuspectedSystemShortcut(signature)` (still a boolean, `signature in` the map) and the new `systemShortcutLabelKey(signature): TranslationKey | undefined`. Both derive from the same single map, so there's no risk of the boolean and the label disagreeing. `TranslationKey` (`keyof Translations`) is now exported from `i18n.ts` so this module's map is type-checked against real locale keys without needing to import the locale JSON files directly. Kept separate from `usageResolver.ts` so the lookup itself (a data/policy concern) stays independently testable from the join/resolution logic.

**Flag carried as a boolean field on `OrphanSignature`/`FlatHotkeyItem`; specific label resolved at render time.** `isSuspectedSystemShortcut: boolean` still flows through `usageResolver.ts` → `sortHotkeys.ts` unchanged (drives which rows get the icon/tooltip treatment). The *specific* label text is resolved only in `grid.ts`, from the row's own `hotkeys[0]` binding via `systemShortcutLabelKey(buildSignature(...))` — avoids adding a second field that would just duplicate what's derivable from data already on the row.

**Visual treatment: label + lock icon distinguish the row; color stays the same as other orphans.** Initially used a `--text-warning` accent color, but the user asked to keep the same (muted/faint) color as a generic "No command" row and rely on the label text + lock icon alone to distinguish a system shortcut. `.hkc-entry-name--system` now only adds icon layout (`display:flex; gap`), no color override — it always renders alongside `.hkc-entry-name--muted`, inheriting that color. Each row's label now comes from `systemShortcutLabelKey` (e.g. "Copy", "Paste", "Move to Line Start") instead of one shared "System shortcut" string, per the user's request to name each command individually. The lock icon (Obsidian's `setIcon` with lucide `lock`, matching the existing icon usage pattern in `toolbar.ts`) plus a `title` tooltip explains why the row can't be bound.

**Platform-aware labels (and now detection) via an injectable `isMac` parameter, not a `Platform` import inside `systemShortcuts.ts`.** The user asked to add accurate Windows/Linux labels despite not being able to test them, since several signatures mean genuinely different things by platform: `Mod` normalizes to `Ctrl` on Windows/Linux, where `Ctrl+Arrow` is conventionally *word*-wise navigation — but the same `Mod+Arrow` on macOS (`Cmd+Arrow`) is *line*-wise navigation (macOS's word-wise equivalent is `Option+Arrow`, i.e. `Alt+Arrow` in signature form). `systemShortcuts.ts` holds two label tables, `MAC_LABEL_KEYS` and `OTHER_LABEL_KEYS` — no longer covering an identical signature set (see the detection decision above) — and both `systemShortcutLabelKey(signature, isMac)` and `isSuspectedSystemShortcut(signature, isMac)` take the platform as a plain boolean rather than reading `Platform.isMacOS` themselves. This matches the project's testability convention (environment-dependent functions take an injectable parameter) and keeps the module free of any `obsidian` import. `isMac` now has to reach `systemShortcuts.ts` from two call sites, not one: `grid.ts` (already imports `obsidian` for `setIcon`) resolves `Platform.isMacOS` for the render-time label lookup, and `state.ts`'s `CheatsheetState.load()` (previously only type-importing `App`) now also imports the `Platform` value and threads `isMac` into `resolveUsage(groups, counts, isMac)`, since detecting *whether a signature is a system shortcut at all* now needs to know the platform too, not just how to word it.

**Option+Shift+Arrow (word selection) added as macOS-only, reusing the Windows/Linux `Mod+Shift+Arrow` selection labels.** `Shift+Alt+ArrowLeft/Right` is macOS's word-selection shortcut (Option+Shift+Arrow), analogous to `Alt+ArrowLeft/Right` for plain word navigation. Its Windows/Linux equivalent is already covered by the existing `Mod+Shift+ArrowLeft/Right` entries (`Ctrl+Shift+Arrow`, confirmed with the user as the standard word-selection convention there), so no separate Windows/Linux entry was added — instead, the macOS entry reuses the same `modal.system_shortcut_select_word_left/right` label keys already defined for that platform's `Mod+Shift+Arrow`, since both express the identical "select one word" concept.

**Undo/redo included despite not being genuinely OS-unbindable.** `Mod+Z`/`Mod+Shift+Z` are normally bound to Obsidian's own `editor:undo`/`editor:redo` commands by default, so in the common case they resolve as ordinary bound entries and never reach the orphan/system-shortcut path at all (unchanged `usageResolver.ts` logic: matched signatures are excluded from `orphans` before the system-shortcut lookup ever runs). The user chose to add them anyway, accepting that the "system shortcut, can't be bound" framing is only strictly accurate for the edge case where a user has removed those default bindings — at that point OS-level undo/redo (present in virtually every text field) still explains why the signature is otherwise unbound, which is the same practical goal as the rest of this feature.

## Risks / Trade-offs

- **[Risk] The set still doesn't cover every OS-reserved combination a user might encounter (e.g. `Mod+Q` quit, `Mod+W` close window) → [Mitigation]** Scoped intentionally to what's been requested; the lookup is a single small module, trivial to extend later without touching resolver/render call sites.
- **[Risk] A user could have genuinely rebound one of these combinations at the OS/Electron level so it does reach Obsidian in their setup → [Mitigation]** Detection only applies to orphans (signatures with no matching bound Obsidian command already); if a user does bind e.g. `Mod+A` to a command, that signature resolves as a normal bound entry, not an orphan, and the system-shortcut label never applies.
- **[Risk] Windows/Linux labels are still unverified on real hardware for the entries that remain → [Mitigation]** The lowest-confidence entry (`Alt+Left/Right` → back/forward navigation) was removed for Windows/Linux entirely rather than guessed at, per user decision; remaining Windows/Linux labels follow well-documented, widely-consistent OS text-editing conventions (Ctrl+Arrow word jump, Ctrl+Backspace delete-word, Ctrl+Shift+Arrow word-select), and are cheap to correct in a single small module if a Windows/Linux user reports otherwise.
- **[Risk] Labeling `Mod+Z`/`Mod+Shift+Z` as a "system shortcut" undersells that they're normally a real, reassignable Obsidian command → [Mitigation]** Accepted trade-off per explicit user decision; the label only ever surfaces when the user has already unbound the default, at which point the OS-level fallback behavior is still relevant context.

## Open Questions

None — the platform-label and undo/redo trade-offs above were confirmed with the user (via explicit choice between presented options) before implementing.
